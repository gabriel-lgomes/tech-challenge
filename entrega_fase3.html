1. Contexto e Objetivo

Esta entrega é uma evolução direta das Fases 1 e 2, que construíram um sistema de apoio ao diagnóstico de câncer de mama com Random Forest, Algoritmo Genético e interpretabilidade via LLM. Na Fase 3, o projeto avança para um nível superior de personalização:

  • Fine-tuning de LLM com dados médicos internos sintéticos (protocolos, laudos e FAQ) — adaptando o modelo ao vocabulário e condutas clínicas do hospital
  • Assistente médico com LangChain — pipeline RAG que combina a LLM customizada com recuperação semântica de protocolos e consulta a prontuários estruturados
  • Fluxos automatizados com LangGraph — orquestração de etapas clínicas (verificar exames, sugerir tratamento, emitir alertas) de forma segura e rastreável
O mesmo repositório das fases anteriores foi utilizado (github.com/gabriel-lgomes/tech-challenge), com a adição da pasta fase3/ contendo todo o código desta entrega.

2. Fine-tuning de LLM com QLoRA

Notebook: fase3/notebooks/01_fine_tuning_colab.ipynb · Biblioteca: Unsloth + TRL

Modelo base e estratégia de fine-tuning

O fine-tuning completo de modelos como LLaMA 7B+ exige 40–80 GB de VRAM — inviável sem hardware dedicado. A solução adotada foi QLoRA (Quantized Low-Rank Adaptation), que congela os pesos originais do modelo e treina apenas adaptadores de baixo rank em precisão 4-bit, reduzindo o consumo de memória para ~6–8 GB (compatível com GPU T4 do Google Colab gratuito).

ComponenteConfiguração
Modelo baseunsloth/Phi-3-mini-4k-instruct (3.8B parâmetros)
Quantização4-bit NF4 (via BitsAndBytes)
Rank LoRA (r)16
Alpha LoRA32
Módulos alvoq_proj, k_proj, v_proj, o_proj, gate/up/down_proj
BibliotecaUnsloth (2× mais rápido que HuggingFace padrão)
TrainerSFTTrainer (TRL) — Supervised Fine-Tuning
OtimizadorAdamW 8-bit · lr=2e-4 · scheduler cosine
AmbienteGoogle Colab (GPU T4 gratuita) ou local ≥8 GB VRAM

Dataset de fine-tuning

Por não haver dados reais disponíveis, foi criado um gerador de dados sintéticos (src/data/synthetic_generator.py) que produz dados realistas no formato instruction-tuning (estilo Alpaca), cobrindo três categorias:

CategoriaExemplosAmostras
Protocolos internosIAM, sepse, controle glicêmico, TVP, antimicrobianos5
FAQ médicaDoses, indicações, critérios de transferência para UTI6
Laudos sintéticosECG (arritmias, BRE, isquemia) e Raio-X de tórax50+

Preprocessing e anonimização

O módulo src/data/preprocessing.py aplica:

  • Anonimização por regex: CPF, datas de nascimento, nomes próprios, CEP e telefones são substituídos por tokens ([CPF], [NOME], etc.)
  • Formatação Alpaca: cada amostra é estruturada com Sistema / Instrução / Entrada / Resposta, incluindo o system prompt de segurança
  • Split treino/validação: 90%/10% com seed fixo para reprodutibilidade
### Sistema:
Você é um assistente médico hospitalar especializado. Responda sempre com base
nos protocolos internos. Nunca prescreva medicamentos diretamente — indique
avaliação médica quando necessário. Cite a fonte ao final de cada resposta.

### Instrução:
Responda à pergunta clínica.

### Entrada:
Qual é a dose de AAS para prevenção secundária cardiovascular?

### Resposta:
A dose recomendada é de 75 a 100 mg/dia, por via oral, preferencialmente com
refeições. Fonte: Protocolo Interno — Cardiologia, revisão 2024.

3. Assistente Médico com LangChain

Notebook/módulo: fase3/src/assistant/chains.py · retriever.py · database.py

Arquitetura RAG (Retrieval-Augmented Generation)

O assistente combina três fontes de informação antes de acionar a LLM:

CamadaTecnologiaResponsabilidade
Embeddingsparaphrase-multilingual-MiniLM-L12-v2Representação vetorial dos protocolos e FAQ
Vector storeChromaDB (persistente em disco)Recuperação semântica por similaridade coseno
Banco estruturadoSQLiteProntuários, medicações, exames pendentes e alertas
LLMPhi-3-mini fine-tunado ou LLaMA 3.1 via GroqGeração da resposta contextualizada
Fallback automático: se o modelo fine-tunado local não for encontrado em models/fine_tuned/, o sistema usa automaticamente o LLaMA 3.1 8B via Groq API (inferência em nuvem, chave gratuita), garantindo funcionamento sem GPU.

4. Fluxo Automatizado com LangGraph

Módulo: fase3/src/graph/medical_graph.py

O LangGraph orquestra um fluxo de decisão clínica completo a partir do ID de um paciente, coordenando 5 nós independentes:

emitir_alertasDetecta situações críticas e grava novos alertas no bancoLista de alertas emitidos

Validação obrigatória: o resumo gerado pelo fluxo inclui explicitamente o aviso "Todas as sugestões requerem validação do médico responsável" — o sistema nunca prescreve diretamente.

5. Segurança e Validação

Módulos: fase3/src/security/guardrails.py · audit_logger.py

Guardrails — limites de atuação

Toda pergunta passa por verificação antes de chegar à LLM:

Tipo de verificaçãoMecanismoExemplo bloqueado
Prescrição diretaRegex em check_input()"Prescreva Metformina para este paciente"
Diagnóstico definitivoRegex em check_input()"Confirme o diagnóstico definitivo de..."
Termos de alto risco na respostaadd_safety_flags()Respostas que contêm "prescrever", "diagnóstico final"
Disclaimer automáticoapply_disclaimer()Anexado a 100% das respostas

Logging estruturado (JSONL)

Cada interação é registrada em logs/assistant.jsonl com rastreabilidade completa: 

{
  "entry_id": "a3f1b2c4",
  "timestamp": "2026-11-17T14:32:01Z",
  "session_id": "d9e2f1a0",
  "node": "assistant",
  "patient_id": "A1B2C3D4",
  "question": "Quais exames devem ser priorizados?",
  "answer": "Com base no protocolo...",
  "sources": ["Protocolo de Controle Glicêmico Hospitalar"],
  "safety_flags": [],
  "requires_human_review": false
}

Explainability — citação de fontes

Toda resposta inclui a seção "Fontes consultadas" com os documentos recuperados pelo RAG (título do protocolo ou pergunta do FAQ), permitindo auditoria e validação pelo médico.

6. Desafios Enfrentados e Soluções Implementadas

DesafioImpactoSolução implementada
Fine-tuning exige GPU dedicada
Modelos 7B+ requerem 40–80 GB VRAM		 Inviável em máquinas locais sem GPU de alto desempenho QLoRA + Unsloth com modelo 3.8B — roda em T4 (Colab gratuito, 15 GB VRAM)
Ausência de dados reais
Dados médicos são sensíveis e regulados		 Impossibilidade de usar dados hospitalares reais Gerador de dados sintéticos com protocolos, laudos e FAQ clinicamente plausíveis + anonimização por regex
LLM sem GPU no ambiente de produção
Modelo fine-tunado exige hardware para inferência		 Sistema não funciona em máquinas sem GPU Fallback automático para Groq API (LLaMA 3.1 8B, chave gratuita) — sem degradação de funcionalidade
Respostas da LLM sem rastreabilidade
LLMs podem gerar informações sem base documental		 Risco clínico de condutas sem protocolo validado RAG com ChromaDB — a LLM só responde com base nos documentos recuperados, que são citados na resposta
Prescrições e diagnósticos definitivos
LLMs podem afirmar certeza médica indevida		 Risco de uso inadequado pelo pessoal clínico Guardrails com bloqueio por regex + disclaimer obrigatório em 100% das respostas + logging de flags de risco
