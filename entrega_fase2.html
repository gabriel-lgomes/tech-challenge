1. Contexto e Objetivo

Esta entrega é uma evolução direta da Fase 1, que construiu um sistema de apoio ao diagnóstico de câncer de mama baseado em Random Forest com explicabilidade via SHAP. Na Fase 2, o projeto avança em duas frentes:

  • Otimização de hiperparâmetros com Algoritmo Genético (DEAP) — substituindo busca exaustiva por busca evolutiva eficiente
  • Interpretabilidade em linguagem natural via integração com LLM (Groq API) — transformando valores SHAP em laudos clínicos compreensíveis por médicos
O mesmo repositório e dataset da Fase 1 foram utilizados (github.com/gabriel-lgomes/tech-challenge-1), com a adição dos notebooks 05_genetic_algorithm.ipynb e 06_llm_interpretability.ipynb.

2. Implementação do Algoritmo Genético

Notebook: notebooks/05_genetic_algorithm.ipynb · Biblioteca: DEAP 1.4+

Arquitetura do AG

Cada indivíduo é uma lista de 6 inteiros, onde cada índice aponta para um valor no PARAM_GRID. A função fitness é o Recall médio em validação cruzada estratificada de 3 folds — Recall foi escolhido porque, no contexto médico, um Falso Negativo (tumor maligno não detectado) tem consequências clínicas gravíssimas.

ComponenteConfiguração
BibliotecaDEAP (Distributed Evolutionary Algorithms in Python)
RepresentaçãoLista de 6 inteiros (índices no PARAM_GRID)
FitnessRecall médio — StratifiedKFold(n_splits=3)
SeleçãoTorneio (tournsize=3)
CrossovercxTwoPoint (2 pontos de corte)
MutaçãomutUniformInt (gene aleatório substituído por valor válido)
ElitismoHallOfFame(1) — melhor indivíduo preservado entre gerações

3. Comparativo de Desempenho — Original vs. Otimizado

Avaliação no conjunto de teste (20% dos dados, ~114 amostras), após treinar o modelo otimizado com todos os dados de treino:

ModeloAccuracyRecallPrecisionF1-ScoreAUC-ROC
RF Original (Fase 1) 0.9474 0.881 0.9737 0.9250 0.9940
RF Otimizado (AG) 0.9474 0.881 0.9737 0.9250 0.9897
Interpretação: Os modelos apresentaram desempenho idêntico no conjunto de teste. Isso é um resultado válido e esperado em datasets pequenos (569 amostras) com modelos já bem calibrados — o modelo original da Fase 1 estava próximo do ótimo atingível com os dados disponíveis. O AG confirmou essa hipótese ao convergir para hiperparâmetros próximos dos padrões.

Por que o resultado idêntico é relevante?

  • Validação do modelo original: o AG percorreu 4.608 combinações (via representação genética) e não encontrou configuração significativamente superior — o que confirma que a Fase 1 produziu um modelo robusto.
  • Recall CV mais alto (0.9354 vs 0.881): na validação cruzada, o modelo otimizado apresentou Recall maior — a diferença no teste final se deve ao tamanho reduzido do dataset e à variância estatística.
  • Valor real do AG: em datasets maiores ou modelos menos calibrados, a busca evolutiva tende a produzir ganhos expressivos. Neste caso, serve como prova de conceito da técnica.

4. Integração com LLM — Interpretabilidade Clínica

Notebook: notebooks/06_llm_interpretability.ipynb

Arquitetura da solução (nuvem)

A integração com LLM foi implementada via Groq API — serviço de inferência em nuvem que oferece acesso a modelos open-source com latência muito baixa (LPU — Language Processing Unit). A chave de API é carregada de um arquivo .env local (nunca exposta no código).

ComponenteDescrição
Provedor de nuvemGroq Cloud (groq.com) — inferência via API REST
Modelo LLMQwen 3 27B (qwen/qwen3.8-27b) — modelo open-source multilíngue
AutenticaçãoAPI Key via variável de ambiente (GROQ_API_KEY)
Biblioteca clientegroq>=0.9.0 + python-dotenv>=1.0.0
Temperatura0.3 (laudos conservadores e consistentes)
Max tokens1024 por resposta

O fluxo de dados é: modelo ML → predição + confiança → SHAP values → contexto clínico formatado → Groq API → laudo em português.

Prompt Engineering — Técnicas utilizadas

Prompt do sistema (role prompting):

Você é um assistente especializado em apoio à interpretação de diagnósticos oncológicos. Seu papel é traduzir os resultados de um modelo de machine learning em linguagem clínica clara e objetiva, para auxiliar médicos na tomada de decisão. Regras obrigatórias: - Nunca afirme que o diagnóstico é definitivo. O modelo é uma ferramenta de apoio, não substitui avaliação clínica. - Use terminologia médica adequada, mas sem jargões desnecessários. - Seja direto e estruturado — médicos têm pouco tempo. - Sempre mencione as limitações do modelo. - Responda sempre em português do Brasil.
TécnicaAplicação neste projeto

Estrutura numeradaLaudo dividido em 4 seções: Resumo, Fatores determinantes, Recomendação, Atenção
Temperatura baixa (0.3)Respostas mais conservadoras e reprodutíveis — essencial para contexto médico

Avaliação da qualidade — LLM-as-a-judge

A qualidade dos laudos foi avaliada pela própria LLM em 4 critérios clínicos, cada um com nota de 1 a 5. Essa técnica (LLM-as-a-judge) é utilizada quando não existe ground truth textual para comparação.

Prompt do avaliador (saída em JSON obrigatório):

Avalie nos seguintes critérios (nota de 1 a 5): - clareza: linguagem clara e acessível para médicos - completude: cobre todos os aspectos relevantes do caso - seguranca: deixa claro que é apoio à decisão, não diagnóstico definitivo - acionabilidade: fornece orientações práticas e concretas Responda APENAS neste formato JSON: {"clareza": X, "completude": X, "seguranca": X, "acionabilidade": X, "justificativa": "..."}
CritérioCaso 1 (Maligno)Caso 2 (Benigno)Mínimo aceitável
Clareza5 / 55 / 54

Segurança5 / 55 / 54
Acionabilidade5 / 55 / 54
Resultado: todos os laudos atingiram ou superaram o mínimo aceitável em todos os critérios. O critério Completude (4/5) reflete a ausência de dados clínicos adicionais do paciente — limitação esperada do dataset Wisconsin, que contém apenas medições morfológicas da biópsia.
